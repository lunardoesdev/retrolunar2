# The tool

Everything below was run; the output is what it printed.

```sh
retrolunar <command> [options] <pack[@sys]>...
```

A target is `pack` or `pack@sys`. A bare name uses the compile-time default system, and
`@native` is another way of spelling that same system.

## Commands

| command | what it does |
| --- | --- |
| `deps` | the resolved graph, leaves first, versions included |
| `search [QUERY]` | what is in the tree |
| `install` | the build script, to stdout |
| `generate` | the same script, with `-o FILE` to keep it and `-x` to run it |
| `env <target>` | the closure's environment as `export` lines |
| `shell` | build the manifest's dependencies, then a shell with that environment |
| `run CMD [ARGS...]` | the same environment, one command |
| `build` | the package this directory is: into the nest, or into `--out DIR` |
| `gc` | remove store entries nothing points at |
| `cache push\|pull TARGET...` | send built packages to a cache, or take them from it |
| `export --to DIR <target>` | a flat bundle of the target, its libraries and what they load, plus the libraries of everything it depends on |

### deps

```sh
$ ./builddir/retrolunar --packages ../retrolunar2-packages deps 'libpng@clang-native'
zlib@source 1.3.1
zlib@clang-native
libpng@source 1.6.48
libpng@clang-native
```

The order is the build order, and a node is a (package, system) pair, so `perl@native` and
`perl@mingw64` are different nodes and both can be in one graph.

### search

```sh
$ ./builddir/retrolunar --packages ../retrolunar2-packages search zlib
zlib                     package  generic, source
zlib-ng                  package  generic, source
```

The third column lists the build files that package has: the exact system's file, the
fallbacks it answers, and `source`. An empty query lists everything.

### install, generate, and the script

```sh
$ ./builddir/retrolunar --packages ../retrolunar2-packages --nest /tmp/nest install 'zlib@clang-native' | head -7
#!/bin/sh
# Generated by retrolunar 2.10.0. Edit it if you like: it is the build.
set -eu

NESTDIR='/tmp/nest'
PACKAGEDIR='/home/satori/ond/git/retrolunar2-packages'
export NESTDIR PACKAGEDIR
```

`generate` prints the same script, `-o FILE` writes it and makes it executable, and `-x`
runs it with `sh` and exits with the script's own status:

```sh
$ ./builddir/retrolunar --packages ../retrolunar2-packages --nest /tmp/nest generate -o zlib.sh 'zlib@clang-native'
retrolunar: wrote zlib.sh
$ sh -n zlib.sh && echo "it parses"
it parses
```

One node of that script, with the parts of it that matter:

```sh
# --- zlib@clang-native (2/2) ---
  _state="$NESTDIR/.retrolunar/state/clang-native/zlib.toml"
  _stored="$(sed -n 's/^fingerprint = "\(.*\)"$/\1/p' "$_state" 2>/dev/null || true)"
  _probes_stored="$(sed -n 's/^probes = "\(.*\)"$/\1/p' "$_state" 2>/dev/null || true)"
    RECIPEDIR='/home/satori/ond/git/retrolunar2-packages/zlib'
    # This node's environment begins where the caller's did: ...
    PATH="$_RL_PATH" CPPFLAGS="$_RL_CPPFLAGS" CFLAGS="$_RL_CFLAGS"
    ...
    WORK="$(mktemp -d "$NESTDIR/tmp/work-XXXXXX")"
    STAGE="$(mktemp -d "$NESTDIR/tmp/stage-XXXXXX")"
    trap 'rm -rf "$WORK" "$STAGE"' EXIT
    cd "$WORK"
    OUTPKG="$NESTDIR/store/9124f0b3f577cf639e5d4ecccf24252cb2fb3614b8616a709a0206827fb8a541"
    DESTDIR="$STAGE"
    PREFIX="$DESTDIR$OUTPKG"
    export OUTPKG PREFIX RECIPEDIR DESTDIR
    SYSDIR="$PACKAGEDIR/system@clang-native"
    export SYSDIR
```

Read down the block and the whole design is there:

- `$OUTPKG` is the entry's final path, and it is named by the node's fingerprint — the
  input hash. `$PREFIX` is where the installer writes *now*, and `$DESTDIR` is what makes
  the difference; the installer is told the final path, so a `.pc` file or a cmake config
  names the directory the package will live in, never a staging one.
- `$RECIPEDIR` is the directory of the recipe that won. `$SYSDIR` is the system's.
- The work happens in `$WORK` under the nest, so a build sees no path in the tree.
- The caller's environment is restored first, then the closure's, then the system's: one
  node's flags are never another's.
- `_stored` is what the state file says, and the node is skipped when it agrees with the
  fingerprint of this node and the environment probes; anything else and the build runs.

### env

```sh
$ ./builddir/retrolunar --packages ../retrolunar2-packages env 'zlib@clang-native' | head -8
NESTDIR='/home/satori/.cache/retrolunar/nestdir'
export NESTDIR
zlib_PREFIX="$NESTDIR/zlib@clang-native"
zlib_source_PREFIX="$NESTDIR/zlib@source"
DEPS="$NESTDIR/zlib@clang-native $NESTDIR/zlib@source"
CPPFLAGS="-I$NESTDIR/zlib@clang-native/include ${CPPFLAGS:-}"
LDFLAGS="-L$NESTDIR/zlib@clang-native/lib -L$NESTDIR/zlib@clang-native/lib64 ${LDFLAGS:-}"
PKG_CONFIG_LIBDIR="$NESTDIR/zlib@clang-native/lib/pkgconfig:...:${PKG_CONFIG_LIBDIR:-}"
```

Every dependency gets `<name>_PREFIX`, the closure's `DEPS`, and the `-I`/`-L` flags for
packages that ship no `.pc` at all; `PATH` and `LD_LIBRARY_PATH` carry native dependencies
only, so a cross toolchain never lands on `PATH`. Using it:

```sh
$ eval "$(./builddir/retrolunar --packages ../retrolunar2-packages env 'zlib@clang-native')"
$ pkg-config --modversion zlib
1.3.1
```

### export

```sh
$ ./builddir/retrolunar --packages ../retrolunar2-packages --nest /tmp/nest export --to /tmp/bundle 'zlib@clang-native'
retrolunar: /tmp/bundle/libz.so.1: rpath rewritten to $ORIGIN (was "$ORIGIN:$ORIGIN/../lib:$ORIGIN/../lib64")
retrolunar: bundle: 2 file(s), 0 unresolved, 0 on the launcher
$ ls -l /tmp/bundle
libz.so -> libz.so.1
libz.so.1 -> libz.so.1.3.1
libz.so.1.3.1
```

What it collects is what the target actually loads, walked through `NEEDED` recursively,
deduplicated by soname, and written flat, because a bundle is not a nest: it is a
directory to hand to a machine that has neither the tool nor the tree. The `$ORIGIN`
runtime path is rewritten to match the flat layout, and anything unresolved is listed —
`--no-rpath` leaves the binaries alone.

## Options

```
--packages DIR   packages tree to resolve recipes from; defaults to
                 $HOME/.cache/retrolunar/packages, cloned from the built-in
                 repository (retrolunar2-packages) on first use
--nest DIR       output root; defaults to $HOME/.cache/retrolunar/nestdir
--cores N        job count for recipes that honour $CORES (default 1)
-o, --output F   write the script to F (generate, build)
-x, --execute    run the generated script (generate)
--out DIR        where build installs the package (also --to)
--repo NAME=URL[@REV]   a repository to resolve against; repeatable
--no-default-repo       do not search the built-in repository
--no-rpath       export: do not bake an $ORIGIN rpath into ELF files
```

The default tree is cloned once into `$HOME/.cache/retrolunar/packages`, and the default
nest is `$HOME/.cache/retrolunar/nestdir`, so a bare `retrolunar generate -x zlib` works
with no options at all.

## Where things land

```
nestdir/
  zlib@clang-native          a symlink to the entry currently built for that node
  store/
    9124f0b3…                an entry: the package's files, named by its input hash
    9816121a…                the same package built from another input
  .retrolunar/state/
    clang-native/zlib.toml   fingerprint, probes, and the tool that wrote it
  .retrolunar/env.sh         the environment `run` and `shell` pass to a command
  tmp/work-XXXXXX/           where a build runs (removed when it ends)
  tmp/stage-XXXXXX/          where an installer writes (renamed into the store)
```

A build keeps its scratch to itself: the work and stage directories are inside the nest,
under `tmp/`, and each node removes its own when it ends, so `/tmp` is never involved and
`nestdir/tmp` is empty again between nodes. The one thing the script cannot choose is where
the nest itself lives — and a nest on a tmpfs is a nest in RAM, so a long build there
(perl's extension build, libjxl) runs the filesystem out of space and dies with `Disk quota
exceeded`, which reads like a broken recipe and is not one. The script says so before the
work starts, with the space left and the flag that fixes it:

```
retrolunar: NESTDIR is on a tmpfs: /tmp/nest (2.1G free of 2.9G)
retrolunar:   a long build can exhaust it; put the nest on disk with --nest DIR
```

## Several builds, one nest

What builds share is the store, and an entry is named by the content of its input — so two
builds of *different* nodes have nothing to fight over, and the nest takes them both at
once. What needs care is the same node twice, and `nestdir/.retrolunar/locks/<node>.lock`
is where that is settled: a node's block takes its own lock before it decides anything, a
second build of that node waits there, and when the first one publishes, the second finds
the node fresh and skips it. Two overlapping invocations of one target therefore cost one
build, not two.

```
$ retrolunar --nest /tmp/nest generate -x 'libpng@clang-native' &   # builds zlib, then libpng
$ retrolunar --nest /tmp/nest generate -x 'zlib@clang-native'       # waits, then: skip zlib@clang-native (fresh)
```

The nest lock (`nestdir/.retrolunar.lock`) is held *shared* by every build for its whole
run and *exclusively* by the commands that move entries — `gc`, `cache push`, `cache pull` —
so those wait for the builds to finish rather than removing an entry one of them is about
to point a name at:

```
$ retrolunar --nest /tmp/nest gc
retrolunar: waiting for the builds in /tmp/nest to finish
retrolunar: 0 entries removed, 4 in use
```

A name is a convenience, never an input: nothing in a build reads `zlib@clang-native`, so
replacing an entry or pruning one cannot break another package's reproducibility. `gc`
removes what no name points at.
